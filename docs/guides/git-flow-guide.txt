1. Структура репозиторію:
Репозиторій розділено на 3 типи гілок: main, develop та feature/***. Кожна з них має свою роль:
- main branch:
    - Роль: Виступає у ролі production branch.
    - Правила: Код застосунку потрапляє на цю гілку тільки в результаті Pull Request (PR) з гілки develop і лише у разі успішного build проєкту.
    - CI/CD: На цій гілці автоматично відбувається збірка Docker images та їх push в Docker Hub для подальшого deploy.

- develop branch:
    - Роль: Гілка для інтеграції та тестування. Це основна робоча гілка, де збираються всі нові features.
    - Правила: Код потрапляє сюди через PR з гілок feature/***.
    - CI/CD: При кожному пуші запускаються автоматичні тести (Unit tests) та Smoke-тест (підняття контейнерів через Docker Compose для перевірки зв'язку backend, DB та frontend).

- feature/*** branches:
    - Роль: Гілки для розробки конкретного функціоналу (наприклад, feature/login-page, feature/api-endpoints).
    - Правила: Створюються від гілки develop. Після завершення завдання розробник створює PR у develop.
    - CI/CD: Проходять базову перевірку lint та запуск тестів backend.

2. Пояснення процесу роботи:
- Перший крок: Розробник виконує команду git clone {link_to_repo} у створеній директорії (також можна використати команду git pull origin develop, якщо віддалений репозиторій уже додано - це можна перевірити командою git remote).

- Другий крок: Розробник перевіряє на якій гілці знаходиться в даний момент за допомогою команди git branch.

- Третій крок: Для початку роботи розробник повинен перейти до гілки develop командою git checkout develop.

- Четвертий крок: Для подальшої роботи розробник повинен виконати наступну команду: git checkout -b feature/{name_of_feature}.
    - Замість {name_of_feature} вказується назва функціоналу (наприклад: feature/backend-login).
    - Команду git checkout -b feature{name_of_feature} повинно виконувати ТІЛЬКИ знаходячись на гілці develop, для отримання актуального програмного коду.

-П'ятий крок: Після завершення написання коду, розробник повинен виконати наступні дії:
    - Переконатися, що всі файли збережені. Команда cd .. зазвичай потрібна лише якщо ви працювали глибоко в підпапках, щоб повернутися в корінь проєкту, де знаходиться .git.
    - Виконати команду git branch, щоб переконатися, що ви у своїй feature гілці.
        - Що робити, якщо змінили код не в тій гілці: Потрібно використати команду git stash (сховати зміни), перейти на правильну гілку командою git checkout і повернути зміни командою git stash pop.

    - Перевірити правильність файлу .gitignore для запобігання push непотрібних елементів застосунку.
    - Виконати команду git add .
    - Перевірити командою git status чи було додано всі необхідні файли (тобто чи було додано файли в яких проводилися зміни).
    - Командою git commit -m "Message" створити commit (Повідомлення повинно бути коротким, але зрозумілим, у теперішньому часі (наприклад: "Add login view and authentication logic").). 
    - Виконати команду git push origin feature/{name_of_feature} (щоб при кожному push не вказувати повний шлях, розробник може виконати наступну команду: git push -u origin feature/{name_of_feature}. Після цього можна буде просто писати git push).

- Шостий крок: Коли розробник впевнений, що завершив роботу над feature, зробив усі commits, а в розділі GitHub Actions Pipeline повернув статус "Success", він створює Pull Request (PR) у гілку develop.
    - У розділі Pull Requests виберіть: base: develop ← compare: feature/{name_of_feature}.
    - Додайте опис змін та надішліть запит на перевірку.

- Сьомий крок: Після того, як ваш PR було прийнято (Merged) у develop, ви можете видалити свою feature гілку. Для продовження роботи над новим завданням повторіть усі кроки, починаючи з третього (не забувши зробити git pull origin develop, щоб отримати свіжі зміни).
